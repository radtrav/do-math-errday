Lesson 0001 · Data Analysis from First Principles cheat sheet · notation decoder · glossary

The Metric Ledger

Every revenue metric is a ratio of four counters — so every revenue story must live in a leg you can name.

The win By the end (~10 min): given any metric claim, you can decompose it into legs and say which leg the story lives in and whether the claimed cause can even reach that leg — unaided.

01There are only four facts

Strip away every dashboard and an ecommerce arm produces exactly four primitive numbers per period. We give each a single-letter symbol, because we'll be writing them constantly:

V = Visits    O = Orders    U = Units    D = Demand ($)

As a TS decoder, that's the whole data model:

type Arm = {
  V: number;   // visits — sessions
  O: number;   // orders — checkouts
  U: number;   // units  — items across all orders
  D: number;   // demand — dollars across all orders
};

Everything else is a ratio of these — not new facts about the world, just views over the same four counters:

CVR = O/V    ConVersion Rate       = Orders ÷ Visits   — how often a visit buys
AOV = D/O    Average Order Value   = Demand ÷ Orders   — how big an order is
UPT = U/O    Units Per Transaction = Units  ÷ Orders   — items per basket
AUR = D/U    Average Unit Retail   = Demand ÷ Units    — price per item
RPV = D/V    Revenue Per Visit     = Demand ÷ Visits   — the headline
// the same five lines, decoded:
const cvr = (a: Arm) => a.O / a.V;  // how often a visit buys
const aov = (a: Arm) => a.D / a.O;  // how big an order is
const upt = (a: Arm) => a.U / a.O;  // items per basket
const aur = (a: Arm) => a.D / a.U;  // price per item
const rpv = (a: Arm) => a.D / a.V;  // the headline

A ratio can move for numerator reasons or denominator reasons — dashboards never tell you which. Keeping the counters visible in the notation is what protects you.

02The tree (it's algebra, not a model)

Multiply CVR by AOV and watch O cancel:

           O     D     D
CVR·AOV = ─── · ─── = ───  =  RPV        so   RPV ≡ CVR · AOV
           V     O     V
Revenue Per Visit ≡ ConVersion Rate × Average Order Value

The triple bar ≡ means "identical by construction" — this is cancellation, not a model, and it cannot be wrong. The same move on U gives AOV ≡ UPT · AUR, so the full tree is:

RPV ≡ CVR · UPT · AUR          (D/V ≡ O/V · U/O · D/U — everything cancels)
Revenue Per Visit ≡ ConVersion Rate × Units Per Transaction × Average Unit Retail

Lifts (ℓ = T/C − 1) inherit the identity, but multiplicatively — this is the form you'll use daily:

(1 + ℓRPV) = (1 + ℓCVR) · (1 + ℓAOV)
(1 + Revenue-Per-Visit lift) = (1 + ConVersion-Rate lift) × (1 + Average-Order-Value lift)

Multiplicatively — not additively. +10% conversion and −10% order size is −1%, not zero. RPV is the area of a rectangle (width AOV × height CVR); watch the area through the two moves — the key piece only exists between the steps:

STEP 0 · start               STEP 1 · CVR +10%            STEP 2 · AOV −10%
                             (grow the height)            (shave 10% of the width — of EVERYTHING)

    1.0                          1.0                          0.9     0.1
┌──────────┐                ┌──────────┐                 ┌─────────┬───┐
│          │                │  +0.10   │ ← gained strip  │  +0.09  │▓▓▓│ ← strip keeps 0.09, loses
│   1.00   │                ├──────────┤                 ├─────────┤▓▓▓│   ▓0.01 = THE CORNER
│          │                │          │                 │         │▓▓▓│
└──────────┘                │   1.00   │                 │  0.90   │▓▓▓│ ← body loses 0.10
                            │          │                 │         │▓▓▓│
area = 1.00                 └──────────┘                 └─────────┴───┘
                            area = 1.10                  kept: 0.90 + 0.09 = 0.99
                            gain = +0.10                 removed: 0.10 + ▓0.01 = 0.11
(1+a)(1+b) = 1 + a + b + ab — the corner ab is the overlap of the gain and the loss

The corner was never part of the original — it's a piece of the gain, alive for exactly one step: the +10% strip you won spans the full width, and the −10% shave removes 10% of everything that now exists, the new strip's right end included. Born in step 1, destroyed in step 2. In shopper terms: the 11th order you won also got its value cut — the corner is that order's haircut. Gained +0.10, lost −0.11, net −0.01, in either order of operations.

The corner grows with the square: ±10% → −1%, ±50% → −25%, +100%/−100% → −100% (double the orders, price them at zero). Same reason a stock that loses 50% needs +100% to get home.

// decoder: the identity, as an assertion that always passes
const closeTo = (a: number, b: number) => Math.abs(a - b) < 1e-9;
closeTo(rpv(arm), cvr(arm) * upt(arm) * aur(arm)); // true for ANY arm

There is no dollar that can move RPV without moving a leg. That's the ledger principle, and it's the first move on any revenue claim: decompose, then ask which leg moved.

03Which leg can a cause even reach?

Legs differ in what kind of thing they are. CVR is behavior — people deciding to buy or leave. AUR and UPT are mix — what and how much they put in the basket. A claimed cause must have a path to the leg that moved:

CauseCan reachCannot reach
Page speedCVR (people leave)AOV / UPT / AUR
Rec modelCVR, UPT, AUR—
One whale orderAOV (as noise)CVR
Trap Diagnosing from RPV directly. RPV inherits the noise of every leg at once, making it the least readable series on the dashboard — yet it's the one stakeholders watch. The decomposition is how you turn their question into an answerable one.

The headline said "test lost 25% of revenue." The ledger says: test converted +71% better and lost everything in AOV — specifically UPT, because control's 10 orders somehow contained 38 units (3.8 items per basket, on ten orders). That's not a treatment effect; that's a couple of whale baskets landing in the control bucket. Any latency story is dead on arrival: latency has no path to UPT.

05Check yourself

How you'd say it to a stakeholder Revenue-per-visit is conversion times order size. On the bad days, more of our visitors bought, not fewer — the entire dip came from a handful of unusually large orders landing on the other side. That's like a casino having a losing night because one player hit a jackpot: it tells you about the player, not the casino.
